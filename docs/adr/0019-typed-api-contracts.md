# ADR-0019: One source of truth for API contracts

**Status:** Accepted (2026-11-14). Roadmap work package 1.3 (`docs/roadmap.md`, Phase 1 and "Architecture gaps": "Hand-written contracts").

## Context
The same request shape is written down up to five times, and nothing checks that the copies agree.

- **Rust.** `pm-service` request types derive `Deserialize` (about 72 derive lines in `crates/pm-service/src`, 25 structs named `*Request`). They carry the real rules in serde attributes, for example `#[serde(default, deny_unknown_fields)]` on `ProofRequest` (`crates/pm-service/src/proof.rs`), and field docs as `///` comments.
- **REST.** `crates/pm-api/src/routes.rs` has about 79 `Json<...>` extractors. Roughly 27 use service types directly (`Json<ReplayRequest>` in `replay`, `Json<ProofRequest>` in `proof_run`, `pm_service::AuthzMatrixRequest`, `ScanTaskRequest`, `EngageFilter`). The rest use body and query structs private to the file (48 derive lines: `CaptureBody`, `SmtpBody`, `UpdateSet`, `HostQuery`, ...), which no other crate can see. Every handler returns `Result<Json<Value>, ApiError>` (`type ApiResult`), so responses have no declared type at all.
- **MCP.** `crates/pm-mcp/src/tools.rs` holds 79 `tool(name, description, json!({...}), &[required])` calls (`tool()` always sets `additionalProperties: false`). The dispatcher in the same file then deserializes with `args::<T>(a)` into the service type, for example `"proof_run" => pm_service::ProofRequest`. The guard test `every_handled_tool_is_listed_and_every_listed_tool_is_handled` in `crates/pm-mcp/src/lib.rs` keeps tool names and handlers in step, but it checks names only, not that a schema matches its struct.
- **SDKs.** `sdk/python/proxymind/__init__.py` (403 lines) and `sdk/typescript/src/index.ts` (506 lines) are hand-written. Many methods take `**inputs` or return untyped `dict`/`Json` (`proof(oracle, **inputs)` in both).
- **UI.** `ui/src/api.ts` (about 380 lines) has about 28 hand-copied interfaces and unions such as `ProofResult`, which mirrors `pm_service::ProofResult` (`#[serde(tag = "status", rename_all = "snake_case")]`). The pages call `api.post<ProofResult>("/proofs", {...})` with inline objects.

**Concrete drift.** `ProofRequest::view_raw` (stored XSS) exists in the struct, in its `///` doc and in the `proof_run` JSON schema, each written separately. The bounds of `samples` (5 to 30) are prose in the Rust comment and `"minimum":5,"maximum":30` in the MCP schema, and nothing enforces them in either place. Neither SDK knows the field exists, and a new oracle such as `marker` (with `marker_kind`) means editing the Rust enum-by-string, the MCP `enum` array, the tool description, docs and the SDK docstrings by hand. `deny_unknown_fields` already rejects unknown fields at runtime, so a stale schema fails late and with a poor message.

There is no `xtask`, codegen crate, `schemars` or `utoipa` in the workspace today (`Cargo.toml` members are `crates/*`; `schemas/` holds only `roe.schema.json`). `deny.toml` allows MIT, Apache-2.0, BSD, ISC, Zlib, MPL-2.0, Unicode-3.0 and AGPL-3.0-only, which covers `schemars` (MIT) and its small dependency set.

## Decision
- **Rust types are the contract.** Request and response types in `pm-service` derive `schemars::JsonSchema` next to `Deserialize`/`Serialize`. `schemars` reads the existing serde attributes (`default`, `deny_unknown_fields`, `rename_all`, `tag`, `skip_serializing_if`), so the schema follows the wire format. Doc comments become `description`. Bounds that matter use `#[schemars(range(min = 5, max = 30))]` and are also checked by the service.
- **Private route structs move.** Body and query structs that live only in `routes.rs` move into `pm-service` (or a `contracts` module in it) so MCP, SDKs and the UI can name them. Handlers return typed responses (`Json<ProofResult>`) instead of `Value`; the serialized bytes stay the same.
- **Generated artifacts, committed:**
  1. `docs/api/openapi.json`: OpenAPI 3.1 for `/api/v1`, one operation per route from a table of (method, path, request type, response type) kept in `pm-api`.
  2. `crates/pm-mcp/schemas/tools.json`: MCP `inputSchema` per tool, built from the request type named in the tool table. Tool descriptions stay hand-written for models, in one `tools.toml` (or doc comments on the types) read by the generator; they are not generated from field names.
  3. `ui/src/api.gen.ts`: TypeScript types only (no runtime code, no new UI dependency). `ui/src/api.ts` keeps the `call()` client and re-exports types.
  4. `sdk/typescript/src/types.gen.ts` and `sdk/python/proxymind/models.py` (`TypedDict`/dataclasses, stdlib only), used by the SDK methods in place of `**inputs` and `dict`.
- **Where it lives.** A new top-level crate `xtask/` (outside `crates/*`, listed in the workspace `exclude` or as a member with `publish = false`) depending on `pm-api`, `pm-mcp` and `pm-service`. It sits above everything, so "lower crates never import higher ones" holds. Run it as `cargo xtask contracts`. TypeScript generation uses a dev-time Node script (`json-schema-to-typescript` in `ui/` devDependencies only) or a small Rust emitter; the choice is left to the implementation, with the rule that nothing generated adds a runtime dependency.
- **Drift check.** A `pm-api` test (or `cargo xtask contracts --check`) regenerates in memory and compares to the committed files; CI fails with "run `cargo xtask contracts`". The existing MCP name-parity test stays and gains a check that every tool maps to a type.
- **Wire compatibility is a hard rule.** No serde attribute changes to make the schema nicer. Golden tests serialize sample values of each migrated type before and after and compare bytes.

## Migration
1. **Done 2026-11-14.** Add `schemars` to `pm-service`; derive it on the ten most used request types (`ReplayRequest`, `ProofRequest`, `AuthzCheckRequest`, `ScanTaskRequest`, `HistoryFilter`, `NewFinding`, `FindingUpdate`, `EngageFilter`, `WsReplayRequest`, `ModelFilter`) and `ProofResult`/`ReplayResult`.
   Deviations: `schemars` 1.2.3 is also a dependency of `pm-store` (owns `HistoryFilter`) and `pm-ai` (the derive had to reach `ExchangeView`, `MessageView`, `BodyView` and `View`, which `ReplayResult` contains; the last two are now re-exported from `pm-ai`); `pm-api` uses it to build the document. The service clamps rather than rejects out-of-range numbers, so the bounds in `#[schemars(range(...))]` (`samples`, `wait_seconds`, history `limit`, `max_pages`, `max_targets`, `max_scan`, `wait_ms` max) describe the effective range; `ProofRequest.oracle`, `ScanTaskRequest.url` and `WsReplayRequest.exchange_id` are marked required in the schema (`#[schemars(extend)]`) because the service rejects them when missing although serde's container `default` accepts that. Golden wire tests: `crates/pm-service/tests/wire_contract.rs` (11 types) and `history_filter_wire_format` in `pm-store`. The "nothing enforces `samples` 5 to 30" claim in Context is out of date: `proof_run` clamps it to 5 to 30.
2. **Done 2026-11-14.** Create `xtask`, emit `openapi.json` for those routes, and turn on the drift check in CI (Linux PR job only, as today).
   Deviations: the route table and document builder live in `pm-api` (`contracts.rs`), `xtask` only writes or checks files, so it depends on `pm-api` alone for now. 14 operations are described; only `POST /replay` and `POST /proofs` have a response schema, the rest still return untyped JSON or a service type without a schema. No workflow change: the `pm-api` test `committed_openapi_document_is_current` runs in the existing `cargo test` job and fails with "run `cargo xtask contracts`".
3. **Done 2026-11-14.** Compare generated MCP schemas with the hand-written ones for the same tools; fix differences in the Rust types (missing bounds, descriptions), not by hand-editing output.
   Deviations: the comparison (`crates/pm-mcp/tests/schema_parity.rs`) covers property names and `required` for the 14 tools that take one of these types. It found eight fields the types accept that the tool schemas omit (`history_search`: `annotated`, `hide_ext`, `hypothesis_id`, `identity`, `status_class`, `text`; `scan_task_start`: `browser`, `record_findings`); they are listed in the test as known gaps for step 4 to remove, because the types are right and no type change closes them. No field is listed by a tool that its type rejects.
4. **Done 2026-11-15** (for the 14 tools that take one of the typed requests). Move MCP tools one at a time to generated schemas; the guard test must pass at each step. Keep prose descriptions as they are.
   Deviations/notes: `input_schema::<T>()` in `crates/pm-mcp/src/tools.rs` builds each `inputSchema` with schemars `inline_subschemas` and no `$schema`, `title` or `$ref`/`$defs`; it turns `Option<T>` into plain `T`, drops `default` and integer `format` names, and turns a `oneOf` of string constants (`View`) into an `enum`. Tool descriptions stay hand-written. Property prose now lives in the field doc comments (hand-written text moved there where it was better, for example `history_search.q`); the eight fields from step 3 are exposed with descriptions taken from the service code. Enums for `oracle`, `marker_kind` and `severity` (the service rejects other values) and `maxItems` 50 for WebSocket `messages` are `#[schemars(...)]` attributes. Bounds the service does not enforce were dropped (`replay_send.max_tokens` max 20000, `ws_send.max_chars` 100 to 20000); `max_tokens` keeps its minimum 200, which the service applies. `schema_parity.rs` now checks properties, `required`, `additionalProperties: false`, a description on every property, and that no schema of the 79 needs `$ref` resolution. The other 65 tools stay hand-written until step 7.
5. **Done 2026-11-15.** Move private `routes.rs` structs into `pm-service`; type the responses; extend OpenAPI to all routes.
   Deviations/notes: 46 request and query structs moved to `crates/pm-service/src/api_types.rs` (`pm_service::api_types`, not re-exported at the crate root); their serde attributes and field names are unchanged (checked against the old source) and `api_types_wire_format` in `wire_contract.rs` pins what each reads, defaults and rejects. Two query structs that only mean something over HTTP stay in `pm-api` and derive `JsonSchema` there (`EventsQuery` for the SSE stream, `BytesQuery` for the exchange detail); `AuthQuery` (`/auth`, outside `/api/v1`) is not part of the API contract. The route table is now `crates/pm-api/src/contract_table.rs`: 175 operations on the 152 paths of `routes::api()` (every method of every route), each with the handler's name as `operationId`. The router is not generated from it, because handlers, body limits and layers differ per route; instead the test `route_table_matches_router` reads the `.route(..)` calls from `routes.rs` and fails on any (method, path, handler) that is in one place only, and `document_covers_every_route` checks the generated document. 125 operations have a typed response schema (they return a service type, which now derives `JsonSchema` together with everything it contains: 227 derive lines outside `api_types.rs`; `schemars` is now also a dependency of `pm-assistant`, `pm-crawl`, `pm-diff`, `pm-fuzz`, `pm-graphql`, `pm-identity`, `pm-ledger`, `pm-model`, `pm-openapi`, `pm-plugin`, `pm-proxy`, `pm-replay`, `pm-scan` and `pm-tools` as needed). The other 50 are described in words, not invented fields: 44 answer with JSON the handler builds on the spot (`json!` or `serde_json::Value`: `status`, `setup`, `exchange`, `model`, the three finding reads and writes, `proof`, `tools/decode` and friends, the `{"deleted": ..}` family, `assistant`, ...) and say which keys they write; 5 are downloads (`ca.pem`, `export/har`, `evidence/pack`, `regress/export`, `report`, with their media types) and `events` is `text/event-stream`. Typing the 44 means giving each a service struct and changing the handler to return it, which is left to a later step because serialized bytes must stay the same. Every operation also lists the `ApiError` body as its `default` response. A type used both in a request and a response (`ScanProfile`, `NetConfig`, ...) appears once in `components.schemas`; where the two readings differ (a field with a serde default is optional in a request but always present in a response) the request reading is kept, which is the looser description of the response. Field docs were added to the request types that lacked them where the meaning is stated in the code; a few nested request types (`Rule`, `Macro`, `Extract`, ...) still have undocumented fields.
6. **Done 2026-11-15.** Generate UI and SDK types; replace the matching hand-written interfaces in `ui/src/api.ts` and the SDK method signatures.
   Deviations/notes: the emitters are about 600 lines in `xtask` (`schema.rs`, `ts.rs`, `py.rs`), with no new dependency. `cargo xtask contracts` writes `ui/src/api-types.gen.ts` and `sdk/typescript/src/types.gen.ts` (the ADR said `api.gen.ts`) and `sdk/python/proxymind/types.py` (`TypedDict`s with a required/optional base-class split, since the SDK supports Python 3.9; the ADR said `models.py`) from the same in-memory document as `openapi.json`. All 286 schemas are converted; untyped (`true`) schemas become `unknown`/`Any`. `--check` fails when any generated file is stale and runs in the Linux CI job. The UI and both SDKs use the generated types where they match, as type annotations only. Many UI interfaces stay hand-written because the contract marks as optional or nullable what the UI treats as required or `undefined`; making the contract match belongs in the Rust types, not in edits to generated files.
7. **Done 2026-11-15.** Delete the hand-written `json!` property maps and `VIEW_SCHEMA` last, when all 79 tools are generated. This closes 1.3 ("the hand-written MCP schemas are gone").
   Deviations/notes: `tool()`, the property maps and `VIEW_SCHEMA` are deleted; all 79 tools use `typed_tool::<T>`, and the dispatch arm of each deserializes into the same `T` with `args::<T>`. Tools that already took a service request type (`SearchRequest`, `RaceRequest`, `FuzzerRequest`, `CrawlRequest`, `NewHypothesis`, ...) use it; the 33 other argument types are new in `crates/pm-service/src/mcp_args.rs` (`pm_service::mcp_args`, all `deny_unknown_fields`; `NoArgs` is the shared type of the seven tools without arguments, and `input_schema` gives it an empty `properties` object because MCP clients expect one). `NewHypothesis` and `HypothesisUpdate` now derive `JsonSchema` and have field docs. Property prose now comes from the field doc comments, which are fuller than the old hand-written text (the old text was kept where it said more). Types that read every field with `#[serde(default)]` but whose old schema listed required arguments (`FuzzerRequest`, `GroupRequest`, `ActiveScanRequest`, `CrawlRequest`, `DiscoverRequest`, `CustomScanRequest`, `DomTestRequest`, `DecodeRequest`, `ImportRequest`, `TokenAnalyzerRequest`, `PluginCheckRequest`, `SearchRequest`, `WsSearchRequest`) mark them with `#[schemars(extend("required" = ...))]`, as step 1 did; serde still accepts a missing field and the service rejects it, so the API is unchanged. Bounds and enums were added only where the service clamps or rejects (`ws_grep` `limit`/`max_scan`, `race_send.count`, `fuzzer_run` `concurrency`/`throttle_ms`, `scan_active` `max_requests`/`oob_wait_seconds`, `discover_content.max_requests`, `custom_scan.max_requests`, `crawl` `max_pages`/`max_depth`, `authz_matrix.max_operations`, `scan_issues.limit`, `token_analyzer_run.samples`, `ws_messages` `limit`/`max_chars`, `replay_group.requests` 2 to 20; enums for `history_grep.part`, `ws_grep.direction`, `scan_issues.min_severity`, `scan_active.checks`, the fuzzer `builtin`, the attack-path `severity`, the organizer statuses, memory `kind` and hypothesis `status`). Dropped because nothing enforces them: `exchange_get.max_tokens` maximum 20000 and the `hypothesis_list.status` enum. `scan_active.checks` now also lists `password_change` and `user_enumeration`, which the service accepted but the old schema left out; `history_grep` now lists the history filter fields it always accepted (`q`, `status`, `status_class`, `source`, `actor`, `identity`, `hide_ext`, `annotated`, `hypothesis_id`, `after_id`, `text`), and `fuzzer_run` lists the `recursive` payload set. Two rustdoc references (`[`BUILTINS`]`, `pm_scan::active::CHECKS`) in field docs were replaced by the values, since models read them. Unknown arguments are now refused for every tool, with an error naming the field (before, 14 tools did this and the rest ignored them, although every schema said `additionalProperties: false`). `history_grep` takes a type with a flattened `HistoryFilter`, where serde cannot deny unknown fields, so its dispatch arm checks the keys against the generated schema (`args_strict`). A missing or `null` `arguments` now counts as `{}` for every tool. `schema_parity.rs` covers all 79 tools (properties, `required`, `additionalProperties: false`, descriptions, no `$ref`; the old `required` lists; enums against the service constants) and `tool_args.rs` checks that a call the old schemas described still deserializes.

## Alternatives
- **OpenAPI first, generate Rust.** One neutral document, strong tooling. But MCP and the byte-exact serde behaviour (`deny_unknown_fields`, defaults) would depend on a generator's output, the service types would become generated code, and MCP tools are not REST routes. Rejected.
- **`utoipa` annotations on handlers.** Mature, gives OpenAPI directly. It puts a large attribute on each of about 150 routes, still needs a second path for MCP and SDK types, and handlers returning `Value` need rewriting anyway. Could be adopted later for the route table only.
- **Keep it by hand plus a drift test.** Cheapest; a test could compare MCP schema keys with struct fields. It still leaves four copies to write, and the SDKs and UI stay untyped. Rejected as the end state; a cheap form of it is a fine stopgap before step 1.

## Consequences
- A new field is written once, in Rust with a doc comment; schemas, SDK types and UI types follow from `cargo xtask contracts`. Stale contracts fail CI instead of failing for an agent at runtime.
- SDK users and the UI get real types for requests and responses.

Risks:
- **Schema differences.** `schemars` handles internally tagged enums such as `ProofResult` well, but `untagged`, `flatten` and custom `Serialize` impls (about 9 `untagged`/`flatten` uses in `pm-service`) can produce `anyOf` shapes that some consumers handle badly. Those types get hand-tuned `#[schemars(...)]` attributes or manual impls, each with a golden test.
- **MCP quality.** Models do better with short schemas. Generated `$ref`, `definitions` and `anyOf: [T, null]` for `Option` are inlined and simplified by the generator; descriptions are reviewed per tool, and the tool descriptions are not generated.
- **Compile time.** The derive adds a little to `pm-service`, already the largest crate (about 21,500 lines). The generator lives in `xtask` so normal builds do not run it; this fits the 1.5 service split.
- **Dependencies.** `schemars` and any TS generator need a pass through the "licenses and advisories" job (`deny.toml`) before merging. If `schemars` is rejected, the fallback is a small in-repo schema walker over the same types.
- **Churn.** Moving the private `routes.rs` structs touches many handlers; each move is its own small change with a wire-format test.
